# SSH Authentication Log Analysis with Splunk

## Objective
Investigate SSH authentication activity and identify repeated failed logons that may warrant review.

## Dataset and Setup
- **Sample source:** [Security datasets — SSH log](https://www.secrepo.com/maccdc2012/ssh.log.gz)
- **Example sourcetype:** `sshlog`
- **Index:** The example searches use `main`; change this to the index used in your lab.
- Confirm the sample's schema and timestamp format before applying the queries below.

## 1. Ingest and Validate
Upload the sample through **Settings → Add Data → Upload**, then confirm events are available:

```spl
index=main sourcetype=sshlog
| head 10
```

Review raw events and the actual field names, including source IP, destination IP, username, and authentication result if present.

## 2. Discover Fields
```spl
index=main sourcetype=sshlog
| fieldsummary
```

Field names and values vary with the log source. Only run the following searches after matching the field names and values to your data.

## 3. Count Failed Authentication Events
If the dataset has an extracted `result` field whose failed value is `failure`:

```spl
index=main sourcetype=sshlog result=failure
| stats count as failed_attempts by src_ip
| sort - failed_attempts
```

If your data uses a different field or value, adapt the filter. A high count is a triage signal, not proof of compromise.

## 4. Identify Sources Above a Triage Threshold
```spl
index=main sourcetype=sshlog result=failure
| stats count as failed_attempts by src_ip
| where failed_attempts >= 5
| sort - failed_attempts
```

The threshold of five is a **starting point for a lab exercise**, not a universal detection threshold. Tune it to event volume and time window. Add a fixed time range or time-binning when assessing bursts.

## 5. Look for Successful Logons from the Same Source
If successful events are available and the result value is `success`:

```spl
index=main sourcetype=sshlog src_ip=<SOURCE_IP>
| stats count by result user
```

Replace `<SOURCE_IP>` with a concrete address, without angle brackets. Determine whether failures were followed by success using event timestamps and the available fields; do not conclude that an account was compromised from correlation alone.

## 6. Investigation Report
Record the time range, source IP, target host, affected account (sanitised), number and sequence of failures, any subsequent success, evidence, plausible benign causes, confidence, and recommended next steps. Correlate with endpoint and identity logs where available.

## Limitations
Shared NAT, forgotten passwords, scheduled jobs, and authorised testing can produce repeated failures. Validate the source, time window, event format, and threshold before raising an alert.
